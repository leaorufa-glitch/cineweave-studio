## 当前视频路由的正式优先级（PD-010）

**用户自有 H3 是长期唯一优先的视频生产主力**；RunningHub 仅在用户自有服务器尚未开机的阶段供可选测试，不是长期并列路由，也不是首批开发或发布的阻断依赖。**服务器目前未开机，无需现在开机**：Film/版本/媒体/Shot/Clip/Mock Provider/Job/审片与 Render 均可先完成。自有 H3 的真实接口应等现有服务运行后核实，不把 Darl 公开“自部署 H3”网关的 content[] 自动认作自有服务器接口。见 [PD-010](../decisions/2026-10-11-H3-SELF-HOSTED-PRIORITY.md)。

## 一、用最少技术部件，保留完整影视专业能力

### 1.1 明确推荐：**单一模块化 Web 应用 + 持久任务 Worker**（不是六个微服务）

面向单人创作者，核心困难不在网站峰值并发，而在**跨多个创作环节不丢状态、媒体版本、异步视频与音画连续性**。推荐从一个可维护的模块化工程起步：

| 工程能力 | 推荐最小组件 | 为什么必须存在 |
|---|---|---|
| 创作者 UI | **桌面优先响应式 Web 应用**（候选：TypeScript / React + Next.js） | 六区同级导航、可编辑剧本、资产整图、导演 Shot/分镜、生产看板、真实播放器和轻时间线 |
| 业务 API / 权限 | 与 Web 同一产品工程的**模块化应用服务**（候选：TypeScript） | 唯一正式对象身份、版本与 AI 提案采纳、授权、费用和跨区影响 |
| 关系与事务事实 | **PostgreSQL**（推荐） | Scene/Shot/Clip 的多对多、正式版本、任务身份、不可变 Run、父续接链及 Render 来源需要可靠事务 |
| 永久媒体 | **兼容 S3 的对象存储** + 元信息 | 图片、音频、源视频、分镜、导出文件必须持久保存，不能仅留过期服务商 URL |
| 异步生产 | 与主应用共享代码/业务数据的**持久后台 Worker** | 模型上传、轮询、媒体拉取、质量检测、DAG 续接、超时恢复和 Render 不能依赖网页开着 |
| 任务队列 | **首选 PostgreSQL 持久任务表/队列**；负载升高再评估专用 Redis/消息队列 | 不为个人项目一开始引入额外维护系统，但要保证可抢占、重试、租约/心跳和恢复 |
| 媒体分析与导出 | **FFmpeg/ffprobe 或等效成熟媒体引擎**，由 Worker 调用 | 真正的视频/音轨检查、非破坏性时间线渲染、格式转换、合并和交付验证 |
| LLM 与模型适配 | 同一应用内的**专业创作服务 + 型别严格的模型 Adapter** | AI 提出专业意见，但长期业务事实与模型真实请求由系统管理 |

**这只是首选架构提议，不是创作者已批准的技术栈**。如果部署环境有现成 Python/ComfyUI 自部署服务，保留最窄的**独立适配器/HTTP 调用边界**，不要求强制把整个 Web 产品改成 Python 多微服务。也不能仅为了“架构看起来专业”引入 Kubernetes、独立矢量数据库、多个 Agent 服务或事件流平台。

### 1.2 按业务边界划模块，不按网页强行拆微服务

**建议模块**：Project/Film/Canon & Screenplay、Asset & Media、Director Shot/Storyboard & Clip、AI Collaboration & Proposal、Model Registry & Compiler、Job/Run/Continuation、Review/Timeline/Render、Authorization & Usage。

模块间基于**稳定 ID、正式 Revision、明确事件或可查询的依赖记录**协作。它们可以先运行在同一个应用进程/Worker 中，未来需要独立扩展再拆部署；不因六个工作区有六个路由就必须有六个 Agent 或六套数据库。

## 二、数据不变量优于过早设计完美 Schema

建议 V1 必须支持而不提前定物理表字段：

- **Project / Film / 可选 Episode/Series**：个人短片起步，允许跨集共享正式资产版本。
- **Story/Canon / Screenplay Revision / Scene / Beat**：剧本正文可编辑，AI 建议与正式采用分离；修改产生受影响对象清单。
- **Character Identity + Look + 一张正式人物整宫格**；**Location + Environment State + 一张正式 1+3 场景板**；**Hero Prop + Visual State + 一张正式 1+3 道具板**；**Voice Identity + 基准语速 + 样音真实状态**。
- **Asset/Media**：真实文件身份、hash、存储位置、类型/尺寸/时间、来源/版本、所用路由上传记录、授权与缺失状态。
- **Director Shot（唯一 ID）**在第 3 区创建；第 4 区补 Shot Execution Design、Storyboard 媒体和 Shot-Clip Mapping。
- **Generation Clip Plan / Compiled Model Input / Run / Take**：每个 ID 和 Revision 的独立性；多次提交不可覆盖；异步任务状态与创作 QA 分开。
- **Continuation Link** 只记录真实父 Run/Take + Motion Context；**Second Sampling Link 是另一种类型**。
- **Timeline Revision / Segment / Render**：非破坏性引用源媒体，真实导出后记录来源和 QC。
- **Proposal / Decision / Finding**：专业 LLM 的编辑建议、系统正式采纳和带媒体时间码的实际观察分别存储。

所有跨区引用采用**明确版本与来源**，不是让 AI 根据一句自然语言在聊天历史里猜最新资产；正式改变时通知待复核的下游计划，历史媒体不被覆盖。

## 三、六区协作不能退化成“填表 → 一键生成”

### 3.1 AI 协作的最小生产合同

1. AI 以**当前选中业务对象 + 正式版本 + 相关剧本/资产/导演要求**形成有针对性的上下文包；
2. 返回与当前专业相关的建议/候选及其**创作理由、具体修改对象、版本影响**；
3. 用户可以直接编辑、比较并采用建议；系统写入正式 Revision，AI 不可直接覆盖“已经正式定型”的故事或资产；
4. 改剧本、人物 Look、场景布局、Director Shot 后，能看到受影响的 Clip/Run/Timeline；只对未执行/新计划标记待复核，历史生成快照保持不变；
5. AI 在第 6 区只有真正访问并分析实际音视频时才可提出“我观察到 XX 秒发生了……”的实媒体诊断。

**不要预设固定六位大师 Agent**。可用同一个 LLM 基础路由根据专业任务与严格上下文包进行角色化协作；未来如质量或成本需要再细分专业服务，但不是 V1 前置条件。

### 3.2 各区在一部电影上的必须完成的实操作

| 工作区 | V1 最小可用真实动作 |
|---|---|
| 1 前期创作 | 编辑 Scene/Beat/对白、AI 深度共创、比较候选并采用 Screenplay Revision |
| 2 资产设计 | 真实生成/导入人物 2×2、场景/关键道具 1+3 整板以及 Voice Identity；真实媒体检查和版本采用 |
| 3 导演创作 | 直接创造/修改专业 Director Shot 的故事目的、镜头/表演/声音要求 |
| 4 分镜与生成规划 | 完善同一 Shot 的画面/时间/台词/语速/连续性，并规划 15 秒内 Clip；支持多 Shot 一 Clip、长 Shot 多 Clip |
| 5 生成制作 | 指定**具体真实 H3 路由**，合法编译/授权/提交/查询/保存真实 Take；DAG 可靠恢复和真续接资格检查 |
| 6 审片与成片 | 真实播放比较 Take、时间码返工、非破坏时间线、音量/声画衔接、可播放成片 Render |

## 四、开发顺序：优先“竖向真实闭环”，而不是把六区各写一个空页面

| 迭代切片 | 可演示、可验收的终点 | 主要验证条件 |
|---|---|---|
| **V0：合同冻结/Mock** | **先做自有 H3 的逻辑适配边界和 Mock**；按需用 GPT Image 2 与 Darl 公开资料制作静态 Fixture；不要求实现完整 RunningHub | 未取得自有协议不得猜字段；Mock 可表达真正父 Take/Context 依赖；无实际能力证据显示未验证 |
| **V1：作品与版本 + AI 剧本** | 建立 Film、创作/采纳有版本的剧本，专业 AI 能实际编辑 Scene/Beat 和提出差异 | 不是只有聊天，正式内容可恢复、可继续导入其他区 |
| **V2：真实视觉/声音资产** | 能真实保存一张人物宫格、场景 1+3、道具 1+3、角色声音身份和语速、来源版本；导入与低成本 Mock 测试通过 | 不是 Prompt 冒充媒体；正式一张整板，不自动拆格，错误能拒绝 |
| **V3：导演 Shot + 分镜 Clip** | 第 3/4 区共用 Shot，完成 22s Shot→B1 12s + B2 10s，以及 2 Shot→一个 12s Clip | 所有资产/对白/动作/声音按时间与版本绑定，导演意图不会被编译重写 |
| **V4：自有 H3 真实生成与恢复** | **等自有服务器可用**后按实际接口完成一个真实短 Clip、下载、音轨/媒体检测、Run/Take；之前仍能完成 Mock/导入媒体链路。RunningHub 可选择用于临时测试，**不代替自有 H3 正式验证** | 自有协议/真实视频与音轨/任务恢复/来源证据通过；服务器未开机时保留明确待联调状态，不要求第二网关先上线 |
| **V5：Take 审片 + 轻量成片** | 比较至少两个真实 Take，裁出来源区间、调整顺序与基本音量并 Render 成可播放影片 | 原始视频不被修改，成片真实文件可独立播放/校验 |
| **V6：DAG + 真续接 + 80s 端到端** | 独立任务并行、B2 等待真实 B1 Take/Context；在接口证据齐全条件下跑真正续接；完整短片从创作到交付 | 换父 Take 不污染子链；不支持真续接时**明确保留待验证状态**，绝不假成功 |
| **V7：质量与成本优化** | 基于真实失败数据优化 H3 模式选择、分镜输入、资产图板可用性、返工路径 | 以每分钟可用成片成本、通过率与返工根因为依据；不是只提高“生成次数” |

优先在 V4 前建立真实媒体与任务系统，避免最后才发现已有视频无法复用/下载。**没有先完整开发所有六区 UI 的前置要求**：每次迭代都推进一个可操作的跨区切片。

## 五、必须先测、不能靠软件架构“设计出来”的能力

| 阻断/证据等级 | 当前状态 | 工程决策 |
|---|---|---|
| **A：用户自有 H3 的实际接口** | 用户明确为长期主力；**服务器暂未开机**，公开 Darl 资料不能代替自有协议 | 先 Mock/设计接口，开机后读取真实协议并联调；RunningHub 仅可选测试 |
| **B：GPT Image 2 生图与编辑** | 已找到 Darl 文档，明确 Base64 输出与尺寸/格式，**未生成本项目图板** | 图板真实生图质量和跨格一致性仍要验证 |
| **C：完整宫格输入 H3 能否保持一致** | 模式允许图片不代表语义理解成功 | 对一张人物整板、场景整板、道具整板分别及组合做小规模视频 QA |
| **D：角色音色/语速和样音参考** | 有音频参考槽位的文档声明，不代表语速精确/声线锁定 | 分开测“输入合法、声音发生、人物声音稳定、台词语速可控” |
| **E：自有 H3 的 Motion Context 原生续接** | **用户报告现有自有服务已实现**；当前服务器未开机且本系统尚未核实调用协议 | **列为主线核心能力**，先完成父 Take/Context 的 Mock 与系统依赖；开机后按实际合同联调，不当成 RunningHub 的可选增值项 |
| **F：最终可用电影质量** | 未实际生成任何一个本项目 Take 或 Render | 通过 80 秒完整实例验收，不能靠文档批准声明成功 |

每个阶段的**“通过”必须有证据类型**：需求批准、文档声明、接口静态校验、Mock 测试、真实网关联通、真实媒体审片、完整影片交付，不可混为一谈。

## 六、工程安全与授权（不可用“开发方便”交换）

- 用户/渠道 API 密钥只保存在服务器环境或密钥管理中；不能提交 GitHub、写前端 JS 或记录在 Run 的可见 Prompt 中。
- 网关响应、任务日志、截图和异常报告避免记录认证头/真实密钥；提示词与媒体可能含私人创作资料，应有限权限访问。
- 真实长期媒体持久化，并记录 checksum、来源、访问权限与可控下载；网关的 COS 签名 URL 可能过期，不可做唯一长期依据。
- 任务重试和预算必须严格受用户授权范围约束；未确认是否远端提交成功时不默认再次收费。
- 复合图板的输入并不等于模型最终正确表现多角度；编辑后的时间线和 Render 都要做真实技术/专业 QA。
- 使用用户提供/授权的声音/图片/视频素材；对第三方人声须明确许可。
- V1 初期可采用单创作者权限模型，但不要把公开仓库、媒体权限和网关 Key 设为完全公开。

## 七、80 秒实例的“产品完整验收”定义

**至少应可证明**：

1. 从 Film/Scene/Beat 发展并修订剧本，AI 对人物动机和剧情冲突提出具体意见，用户能实际采纳；
2. 角色 Look 2×2、车站 1+3、旧钥匙 1+3 以**整张真实媒体**绑定到 Shot/Clip；声音身份有基准语速，样音实际状态可见；
3. 第 3 区一个真正的 22 秒 Director Shot，第 4 区规划 12+10 两 Clip，没有强制电影切镜；
4. 12 秒多镜头 Clip 可关联两个导演 Shot，模型是否按计划生成由真实媒体确定；
5. 针对两类 H3 路由能正确**静态编译/解释状态**，一切收费调用都有授权；受支持的模式真正下载了视频；
6. 生成失误（角色漂移、空间跳变、钥匙形状/左右手、声音音色/语速）能够通过真视频时间码定位资产/导演/分镜/模型/后期；
7. B2 仅在真实 Context 存在时称为原生续接；父 Take 改选后旧续接链保留并标注失效/分支；
8. Take 对比、非破坏编辑、混合音画与完整影片实际 Render 后能播放，媒体及版本来源清楚；
9. 浏览器关闭、任务超时/失败、跨工作区修订均不能让付费媒体和正式版本丢失；
10. 以真实的任务/媒体/成本/质量证据评估系统是否比纯手工反复抽卡更能稳定产出优秀作品。

若无法获得自部署真续接合同，也可先让**独立 Clip 的完整创作→生成→审片→成片闭环运行**，但在产品上必须明确将“同一长 Shot 的真续接验收”列为未通过的必做项，不用伪续接宣称整体验收完成。

## 八、下一轮唯一需要的集中审定与证据

**建议创作者只针对三类重要方向集中给意见**，无需逐字段批准：

1. 是否批准 **“模块化单体 Web + 持久 Worker + Postgres + 对象存储 + 可靠媒体处理”** 为 V1 技术方向（具体库和部署方式仍可调整）。
2. 是否批准 **“真实跨区闭环优先，不建一堆占位六区页面；只用合法 H3 模式，不替用户偷偷剪镜或拆正式宫格”** 的工程顺序。
3. **等自有 H3 服务器开机时再联调**：取得自有 API/已有原生 Motion Context 续接调用协议与一个授权测试预算；现在只需 Mock 和无付费开发，不要求立刻开服务器，**不把 RunningHub 适配当首发前置条件**。

此阶段不发起真实模型调用、不启动 Codex 工程、不部署应用；凡技术实现与收费测试另待用户明确启动。
