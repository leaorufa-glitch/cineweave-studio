# V1.2-02｜用户／系统／AI 三层协作机制

> 状态：**详细设计草案，待审定**；日期：2026-10-10  
> 依据：V1.1 已确认产品基线，特别是“专业 LLM 贯穿六区”与“正式工程状态由系统管理”。

## 0. 正确理解“三层”

三层是**职责分工**，不是从用户→系统→模型的单向制作阶段。六大工作区是用户的影视业务视图；专业 LLM 在全部六区提供持续智能；系统层贯穿六区持有长期项目事实、负责合法执行。

| 层次 | 负责任务 | 不负责的事情 |
|---|---|---|
| 用户层 | 故事目标、表达偏好、创作编辑、方案比较、授权、采用 Take、最终成片判断 | 不要求用户手工处理 API、队列、版本传播 |
| 系统层 | 同一工程的真实事实、对象身份、版本、上下文、正式采纳、依赖、模型编译校验、任务调度、费用、媒体与导出 | 不假装纯算法可以替代专业剧作/导演创造力 |
| AI 层：专业 LLM | 在六区进行构思、写作、诊断、分析、专业判断、提案、跨区反馈；使用完整准确的工程上下文 | 不自行充当不可审计的数据库、任务队列或长期唯一记忆 |
| AI 层：多模态生成 | 根据合法正式任务生成参考图、音频、音视频；实际输出供审核和使用 | 不独立决定整部影片的创作方向或覆盖正式工程数据 |

注意：AI 层含 LLM 与图像/音频/视频生成模型。LLM 是否由一套多角色系统、分任务调用或多种模型组成，是**后续待定实现问题**，不能在 V1.2 写死“必须 N 个 Agent”。

## 1. 共同的专业 AI 交互模式

所有工作区使用相似但专业内容不同的创作协作生命周期（**拟定机制，不强制每次人工确认**）：

1. **确定任务与版本上下文**：系统记录 Film、当前 Scene/Beat/Asset/Shot/Clip、版本、授权范围、已有决定与完成标准。
2. **专业 LLM 工作**：围绕明确专业任务创作、比较方案、提出判断与诊断；必要时基于多模态真实结果分析。
3. **返回候选产物**：用可追溯、可比较的提案/修改差异/检查结论表示，而不是直接覆盖正式内容。
4. **系统验证**：核对对象身份、引用、版本、必填内容、合法参数、文件是否存在、任务依赖是否合法。
5. **合法采纳**：根据用户明确操作或事先授权策略，把候选转为新正式版本，并记录原因及来源；不采用则保留候选而不污染已确认作品。
6. **影响传播**：发现下游引用到变更的旧版本时，标记需要复核并支持定点返工；保留已有媒体和历史选择。
7. **继续协作**：AI 可接着之前工作结果提出下一步，不需要重新猜整部作品背景。

系统可以按照“专业风险和已授权范围”自动执行低风险步骤；并不是让用户对每一句对白、每张分镜都按一次批准。

## 2. 六区专业 LLM 责任矩阵

| 区域 | 必须能胜任的专业智能 | 典型可审阅产物 | 避免的低质量行为 |
|---|---|---|---|
| 1 前期创作 | 戏剧结构、人物弧光、目标与阻碍、因果、冲突升级、悬念、节奏、对白创作与批评 | 故事备选、剧情大纲、剧本修订、Scene/Beat、诊断与改稿理由 | 只填格式完整的剧本，忽视故事是否好看 |
| 2 资产设计 | 角色形象、选角感、场景空间、服化道、人物声音与视觉统一性 | 美术方向、资产需求、参考职责、造型备选及评估 | 仅给文字标签，声称已经拥有真实图片/声音 |
| 3 导演创作 | 场景表达、表演与潜台词、Blocking、摄影机与声音语言、导演 Shot 判断 | 导演方案、Shot 意图、表演与视听调度选择理由 | 所谓导演只输出空泛风格形容词 |
| 4 分镜与生成规划 | 同一 Shot 的视听时序、构图/运动、动作/台词、跨镜连续性、Clip 实现策略 | 分镜、Shot 执行设计、Clip Plan、续接可行性与风险分析 | 无授权重写导演意图、按模型限制随意增加剪辑切点 |
| 5 生成制作 | 目标模型语义编译、输入质量复核、真实结果与失误归因 | 编译提案、修订差异、Take 评审建议、局部返工方案 | 以文字“生成成功”替代真实媒体检查 |
| 6 审片与成片 | 表演/情绪/叙事、镜头衔接、节奏、对白与声音、整片完整度诊断 | Take 审阅、选用理由、时间线建议、问题单、成片评议 | 把所有问题都归因于“再抽卡”或靠后期补救 |

专业 LLM 必须理解上下游因果：导演以剧本人物目标为依据；分镜以导演意图为依据；审片同时看剧本叙事意图与真实素材，不是孤立评审一段视频。

## 3. “上下文”不能等于聊天记录

系统按任务构造**有版本指向的创作上下文包**（字段为概念建议）：

- **身份**：项目/单集/Scene/Beat/Shot/Clip 和所绑定资产的稳定 ID 与版本。
- **正式内容**：当前采用的剧本、角色事实、世界规则、导演决定、镜头与声音要求。
- **任务相关历史**：重要已采纳选择、此前失败/退回原因、可用候选与反对理由；不必塞入全部无关聊天。
- **可验证素材**：真实媒体 ID、可访问状态、必要多模态预览与元数据。
- **专业目标**：当前问题、要交付的产物、评价维度、可变更边界、受保护的导演/剧情要求。
- **执行约束**：用户授权级别、预算、可用模型能力、时长和续接父子引用（适用时）。

这些上下文应该能被重建、检查与重新调用。与仅依赖 LLM“记得上次聊到哪”相比，这才是项目长期可靠性的基础。

## 4. 创作结果、正式采纳与授权

### 4.1 建议区分三类结果

- **Proposal／草案**：AI 或用户提出的备选，不改变当前正式作品；可比较与评论。
- **Committed Revision／正式版本**：经权限规则采纳的内容，成为后续任务的事实来源；记录父版本。
- **Review Finding／审查意见**：指出问题、提供依据和修改建议，可生成提案，但单靠审查意见不能更改正式内容。

这些是业务概念，字段名、持久化方式和 UI 操作仍待详细设计。

### 4.2 权限策略（建议，不是已确认门槛）

| 类别 | 示例 | 推荐默认行为 |
|---|---|---|
| 重大创作改动 | 核心情节反转、角色动机改写、关键导演长镜头替换 | 明确用户采纳或遵从用户预先设置的具体授权策略 |
| 常规创作细化 | Shot 已确认前提下的镜头内动作时间建议 | 允许候选自动生成；按授权可自动保存细化草案 |
| 真实生成成本 | 提交视频批量生成、超出预算、产生重复计费风险的重试 | 提交前预算/批次授权；只允许授权范围内自动调度 |
| Take 采用与最终成片 | 选定上游续接父 Take、采用最终剪辑版本、成片发布 | 保持清晰可审阅的采用决定，允许预设自动放行但必须可追溯 |

“审核”与“确认”不意味着每一步都弹窗。设计目标是**高创作控制、低操作摩擦**。

## 5. 跨区专业协作：实例

**场景 A：审片发现剧情问题**

第 6 区发现“女儿突然原谅父亲”缺少充分铺垫。专业 LLM 引用真实影片片段与正式剧本，生成问题报告；系统关联 Scene/Beat 和受影响 Shot。第 1 区提出增写/改写的剧本方案；用户采纳后，系统标记相关导演方案、Shot、Clip 与 Timeline 需要复核。旧生成视频不被删除。

**场景 B：分镜发现导演长镜头超出单次时长**

第 3 区确定 24 秒不切镜表达。第 4 区检查 H3 V1 单 Clip 15 秒规划上限，建议跨 2 个 Generation Clip 并评估原生 Motion Context 续接；如真实服务模式不支持，就退回导演评估替代方案。第 4 区不能默默拆成两个剪辑镜头。

**场景 C：自部署续接父 Take 变更**

第 5 区使用 Run-A 所产 Take-A 生成子续接；之后用户改选同一父 Clip 的 Take-B。系统标记旧子链不再代表新父选择，建议重新执行依赖分支。专业 LLM 评估新父质量和动作衔接；无依赖的其他 Clip 不受阻塞。

## 6. 生成模型与聚合站的职责

- 所有模型经用户既有聚合中转站接入，默认文本模型记为 `deepseek-v4.1-flash`，默认图片模型记为 `gpt-image-2`；这属于用户指定配置，**不表示已经完成真实连通性/能力验证**。
- H3、Seedance、Wan3 的模式、参数、媒体输入和返回结果要经过模型专属能力检查与编译，不能共享“万能提示词”或臆测兼容。
- 系统在已授权前提下提交模型任务，追踪真实 Run；LLM 参与语义编译与结果诊断，但不自己更新费用账本和任务状态。
- 对 H3 原生续接与 RunningHub 路由必须分别核验。命名相同不等于续接能力相同。
- 真实密钥不是产品设计文档的一部分，不写入此公开仓库。

## 7. 一份专业 AI 任务合同至少要覆盖什么（待 V1.3 定格式）

| 合同元素 | 最小含义 |
|---|---|
| Task Intent | 当前具体专业目标及需要解决的问题 |
| Input Snapshot | 全部实际采用的工程对象、版本与相关媒体 |
| Allowed Changes | 本次允许提出或应用的修改边界 |
| Output Proposal | 可审阅的方案/差异/诊断/生成计划 |
| Quality Evidence | 为什么此方案服务人物、戏剧、导演与视听目标 |
| Validation | 可用系统规则检验的身份/引用/时长/媒体/依赖等 |
| Adoption Rule | 谁/何种授权可以采纳，如何记录来源 |
| Downstream Impact | 采纳后可能需要复核的下游对象 |

暂不在此阶段固定 JSON Schema、Agent 名称、模型温度、编排框架和内部 API。

## 8. V1.2 审阅问题

1. 六区 LLM 是否能“深度专业共创”，同时不要求用户逐项审核机械性输出？
2. 专业诊断是否附带依据，并能定位到相应 Scene/Shot/Clip/Take？
3. 采纳建议后是否由系统保存正式版本与受影响范围？
4. 模型执行是否必须经过合法性和费用/授权机制，而不是 AI 直接随意调用？
5. 同一项目是否能从已有剧本、资产、Shot 或 Take 进入而不重做前面所有内容？
