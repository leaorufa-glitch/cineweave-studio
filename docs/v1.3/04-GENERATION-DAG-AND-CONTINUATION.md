## 一、我们要实现的不是“一个生成按钮”

对于一部短片，模型生成需要应对：批量独立镜头、跨 Shot 的多镜头生成、连续长 Shot 跨 Clip、候选 Take、续接上下文、失败恢复、费用授权、并发队列和最终审片。这些都必须归属于同一影视工程。

核心设计要求：

- **生产任务以实际依赖组成有向无环图（DAG）**；没有依赖的 Clip 可以在资源和预算允许时并行。
- **故事顺序 ≠ 执行顺序 ≠ 最终剪辑顺序**。不能因为 B 片段在 A 之后出现，就认为 B 必须等待 A。
- **原生续接不是“相邻 Clip + 上一段末帧”**：只有真实父运行结果和可用 Motion Context 才能建立续接。
- **每次模型提交都是独立 Run**，保留输入快照、任务状态、真实结果和错误证据。
- **同一 Clip 可以产生多个 Take**，父 Take 的选择决定真实续接的下一段依赖，不得在用户改选父片时隐式沿用旧子链。

## 二、Clip Plan、运行、Take 与续接的关系

| 对象 | 身份与内容 | 是否可以有多个？ |
|---|---|---|
| Generation Clip Plan | “希望生成什么”，与 Shot/资产/声音和计划时间绑定的版本化方案 | 计划有修订；一个 Shot 可跨多个 Clip |
| Compiled Model Input | 针对目标模型与模式编译后的**不可变请求快照**，含真实参考引用、合法参数 | 同一 Plan 可编译多个模式或修订 |
| Generation Run | 一次实际生成尝试，记录模型、路由、请求、远端身份、状态、费用依据 | 一个 Plan 可有多个 Run |
| Take | 已获得的真实生成媒体候选，记录媒体、来源 Run、质量观察和采用状态 | 一个 Run 根据实际服务返回规则可以有一个或多个 Take |
| Motion Context | 由实际运行产生并可用于下一段原生续接的上下文记录/引用 | 是否存在、如何绑定及有效期要按真实路由验证 |
| Continuation Link | 真实父 Run/Take/上下文 → 子 Run 的依赖与来源 | 某 Clip 不一定具有该依赖；可形成多条候选历史链 |

**业务不变量**：B2 可依赖 B1 的 *Take-02*，而不是模糊地依赖“Clip B1”；如果服务端上下文实际仅与父 Run 关联，系统也必须能证明它对应哪个被采用的父结果。

## 三、原生续接的两阶段判断

### 阶段 A｜规划续接（第 4 区）

专业导演与分镜先决定：这是否是同一时间/动作/摄影机/表演过程的自然延续？是否存在有意义的切镜？长镜头是否需要跨 15 秒生成限制？

产出的是**建议续接的 Clip Plan 和预期依赖**，状态仍然只是规划；不允许声称已拥有实际上下文。

### 阶段 B｜实际续接（第 5 区）

提交子 Run 前必须验证：

1. 父 Clip 的目标版本和实际父 Run/Take 存在。
2. 父 Take 已按当前策略通过足够的审看与采用决定。
3. 真实路由确实产生了当前可用且对应此父 Run/Take 的 Motion Context。
4. 子目标模型/模式、相关参考、时长及上下文能力兼容。
5. 所需素材文件可访问，编译后的请求及参数合法。
6. 当前执行预算、授权、并发资格与任务状态允许提交。
7. 子 Run 记录不可变的父引用，并能够与原 Clip/Shot 映射追溯。

全部成立才可提交**真正的原生续接**。否则，进入“等待上游/待补充条件/不可续接/待导演评估其他方案”等明确状态，不能降级却仍标记为续接成功。

## 四、对续接概念的严格区分

| 技术策略 | 利用什么 | 是否等于原生续接？ |
|---|---|---|
| 独立生成 | 剧本、分镜和资产参考 | 否 |
| 首帧/首尾帧约束 | 选定的图片参考作为视觉边界 | 否 |
| 上一段末帧作为参考 | 从上一 Take 提取的静态画面 | 否 |
| 以先前视频作为通用参考 | 模型支持的参考视频输入 | 不一定 |
| **原生 Motion Context 续接** | 该服务实际保存并允许续用的运动/时间上下文 | **是：有可核查的父运行关联时** |

用户此前已实现自部署 H3 原生续接，这是**用户报告的已有能力**；当前给出的 RunningHub 文档是否暴露相同能力，需要按具体 API 路由单独核对，不把两个渠道混为一谈。

## 五、任务 DAG 的执行行为

假设 80 秒案例的 Clip 为 A1、A2、B1、B2、B3、C1、C2。

- A1、A2、B1、B3、C1、C2 **没有真实续接边**：可以在模型并发和预算许可时调度并行；不需按故事顺序强制等待。
- B2 是 B1 中同一 22 秒长 Shot 的原生续接候选：B2 必须等待用户选定、质量合格的 B1 实际 Take 和可用 Motion Context。
- 如果 B1 提供 Take-01、Take-02，而用户选 Take-02，B2 的续接输入不能仍指向 Take-01 所属上下文。
- 如果 B1 失败或尚无可用上下文，B2 进入真实等待/阻塞状态；其他无依赖任务不因此停止。

**注意**：“允许并行”并不等于一定同时调用 N 个模型。实际执行需考虑中转站并发额度、图片/视频共享资源、批次预算和用户授予的许可。

## 六、建议的任务状态（工程合同草案）

Run 的运行状态与 Clip 的创作/审核状态需分开。建议至少区分以下概念：

| 类别 | 状态例子 | 含义 |
|---|---|---|
| 计划准备 | draft / needs_validation | 方案未就绪或当前版本未验证 |
| 等待条件 | waiting_reference / waiting_parent / waiting_approval | 缺素材、无合格父 Take/上下文、等待生成授权 |
| 可执行 | ready / queued | 已通过检查，在队列中等待资源 |
| 提交过程 | submitting / submitted / running | 正在提交、远端已接收、持续运行 |
| 不确定 | submission_unknown | 网络超时导致无法确定远端是否实际收到任务 |
| 结果 | completed / failed / cancelled | 本次真实执行的最终状态 |
| 质量与采用 | take_pending_review / accepted / rejected | **对 Take 或候选进行审片和采用**，不能直接等同于 Run completed |
| 版本影响 | stale / needs_replan | 方案或子链引用到已变更的旧版本，需要针对性复核 |

具体枚举及状态转移可以在工程设计阶段精简；必须保留“远端执行成功≠视频可用”的含义。

## 七、可靠提交与失败恢复

### 7.1 不重复提交高成本任务

一次生成任务至少要有稳定的本地任务身份和不可变输入快照。提交前记录授权范围、所用模型/路由、参考、关联版本及唯一提交意图。

如果发生“请求发送了，但响应超时”，不能简单立刻再发一次并假装第一次不存在。应优先通过中转站提供的实际状态查询/任务检索能力核对（**是否支持需验证**）。无法确认时标记“提交未知”，由规则或用户决定如何处理重复计费风险。

**幂等能力不能靠设计文档宣称网关天然支持**；实现要根据实际接口的任务 ID、幂等键或请求可追踪性选择策略。

### 7.2 失败分类

- **输入错误**：参考缺失、格式不合法、参数越界 → 不盲重试，回到编译/素材修正。
- **临时执行失败**：远端故障、偶发超时、排队失败 → 有界重试和资源退避，不超预算。
- **创作失败**：视频任务“成功”，但人物、动作、对白或导演表达不合格 → 进入专业问题归因；可能要求修改剧本/导演/分镜，不应无限抽卡。
- **上下文失败**：缺 Motion Context、父 Take 不合格、选错父结果或模型不支持 → 不提交真正原生续接；明确依赖原因。
- **预算和授权不足**：任务暂缓，保留规划与已生成数据。
- **取消或中断**：保留远端真实状态和本地历史，承认某些路由可能不支持有效取消或退款。

### 7.3 重启后恢复

系统应保存任务、远端 ID、轮询/回调信息和生成结果位置；浏览器页面关闭、程序重启或 Worker 变更不应导致已经提交的任务消失，也不应自动重发未知任务。

## 八、父 Take 改选时的版本与分支

假设 B2-RunX 使用 B1-TakeA 续接成功，用户后来决定采用 B1-TakeB。

系统应：

1. 保留 B1-TakeA、B2-RunX、B2-TakeX 的历史及实际媒体；
2. 明确显示 B2-TakeX 属于**旧父选择的续接分支**，不能悄然宣称与 B1-TakeB 连续；
3. 将面向“当前父选择”的后续续接任务标记待复核/重新生成；
4. 对独立 Clip 完全不产生阻塞；
5. 提供用户可审阅的选择：重新基于 TakeB 续接、沿用旧分支作为另一剪辑版本、或回导演/分镜改造拍法。

这种处理保留创作自由与生产历史，避免强制删除昂贵生成结果。

## 九、成本、授权与调度

推荐在实际生成前明确批次范围、每模型路由预计费用/额度和调用授权，支持用户预设预算与允许的自动重试范围。系统应该：

- 对新提交、重试、续接子链分别计算可用余额/预算许可；成本估计和真实记账分开。
- 对独立任务使用可控并行；对续接链按真实父依赖触发。
- 避免同一素材版本变化后仍不加提示地提交旧 Compiled Input。
- 记录每次真实调用、失败、手动取消和用户选择，支持审计与定位昂贵返工原因。
- 成本控制是基础系统能力，但不能以“便宜”为由擅自改变必要的故事和镜头表达。

## 十、验收情况如何定义

未来端到端工程测试至少覆盖：

1. B1 尚未有父 Run/Take，B2 不提交；其他独立 Clip 可提交。
2. B1 有两个 Take，B2 必须绑定当前**被选用的真实 Take 对应上下文**。
3. 改选父 Take：只影响真实下游续接分支，不删除历史，也不阻塞无关任务。
4. 父 Run 成功却无 Motion Context：B2 不被标为原生续接成功。
5. 首尾帧/末帧参考不得被当成 Motion Context。
6. 模型不支持某续接组合时，系统能回到计划/导演层提出替代，而不是发出非法请求。
7. 提交后网络超时：系统进入“状态未知/核对”而不是默认重复计费。
8. 浏览器关闭重开后真实任务仍可追踪。
9. Clip 成功却 Take 质量差：用户仍可退回 Shot/Clip 计划或生成，不能只标记“全部完成”。

**本文件不声称当前网关已经实现上述机制；它定义未来软件必须正确处理的业务条件。**
