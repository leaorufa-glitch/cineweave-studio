## 1. 设计原则：先创作视听，再编译模型输入

正式的影视需求先存在于**模型无关的 Audiovisual Execution Plan（视听执行计划）**，然后才由第 5 区根据目标模型能力编译。

理由：

- 专业导演/分镜不应为了某一 API Prompt 字段而丢失镜头表达和人物行动。
- 同一个 Shot 或 Clip 可在 H3、Seedance、Wan3 等支持条件下执行不同版本，不改变其专业创作身份。
- 模型模式/参数更新只需要更新对应编译器和能力记录，不应该把剧本、Shot 和资产设计全部重写。
- AI 对 Prompt 的语言编排属于智能创作，但**最终提交格式、字段类型、文件引用和合法参数必须确定性验证**。

## 2. 推荐两级编译（产品业务概念）

### 一级：影视创作计划 → 标准视听执行计划

输入由第 3/4 区产生：

- 当前正式 Script / Scene / Beat / Director Shot 的版本与表达目标；
- Clip 计划时长，镜头顺序/时间区间/切镜意图；
- 主体行动、场景空间、物体状态、摄影、光线与风格；
- 原生音画要求：对白（保留原文）、说话者、人声身份、时间、环境声、拟音、音乐和停顿；
- 真实 Asset/MediaFile 与参考职责/版本；计划起止连续状态；
- 独立/参考/拟原生续接策略及导演级不可更改项。

输出是**可供审阅、模型无关、版本化**的视听执行计划。如果计划表达不清或缺文件，应在编译之前暴露，而不是交给视频模型猜。

### 二级：标准视听执行计划 → 指定模型模式的 Compiled Input

模型适配器根据当前**已验证**能力确定：

- 目标模型和运行路由、可用生成模式、合法时长和画幅；
- Prompt 的结构、镜头段落、音频/声音字段、参考资料使用与标签；
- 文件上传/媒体 URI 的实际约定、身份/关键帧等参考槽位限制；
- 原生续接真实输入条件、父 Run/Take 上下文；
- 正式请求参数和必要的模式专属约束；
- 预计费用/时延风险及不可执行原因；
- 经过系统合法性检查的**不可变编译快照**。

模型适配器不仅是“把通用中文 Prompt 翻成英文”；它要表达视频模型**真实支持的可调用能力**，并保留导演的叙事时间和重要对白。

## 3. H3 的 Prompt 编排重点（待按实际资料细化）

用户明确希望充分利用 H3 的多镜头、原生音画、多模态参考，以及已自行实现的原生 Motion Context 续接。

应设计能力矩阵而非一个“万能 H3 Prompt”：

| 待核对能力 | 需要确认的内容 | 为什么重要 |
|---|---|---|
| 多镜头 | 目标路由支持的 Shot 组织格式、切镜边界、时长控制 | 一个 Clip 可以包含多个 Director Shot |
| 原生音画 | 对白、角色声音、环境声、非画内音乐怎样合法指定 | 镜头内动作与对白的时间不能互相打架 |
| 多模态参考 | 图片/音频/视频各模式的限制、标记、职责与组合方式 | 真实参考资产绑定必须可执行 |
| 首帧/首尾帧引导 | 各种模式是否支持，生成效果与输入要求 | 正确选择独立生成与参考引导 |
| 原生续接 | **自部署服务的实际路由**、首段是否需保存上下文、父 Run/Take 与 Motion Context 如何传递 | 保证长镜头跨 Clip 的真正连续 |
| 多版本/子模型 | 同品牌不同变体的能力是否不同 | 防止将某变体功能错误迁移到另一个 |
| 运行状态 | 提交、查询、取消、失败、媒体返回及上下文存储机制 | 批量 DAG、费用控制和恢复正确性 |

用户以前提供过 H3 提示词规范材料；其可读性与版本、模式适配仍需在实施前逐项核实。**本阶段不根据不完整资料把某一个 Prompt JSON 字段定为唯一官方合同**。

### 对对白的特殊要求

- 影视导演和剧本中已确定的中文对白，除非用户要求改写，否则编译器不得为追求提示词优化而擅自修改语义或内容。
- 可针对目标模型语言习惯组织画面说明，但要明确台词“逐字保留”与专业创作时“提出改写建议”是不同权限。
- 切镜、运动、环境声和音乐的结构化编排应忠实保留该 Clip 的 Shot 顺序和相对时序。
- 同一人物在不同 Shot/Clip 的声音身份要能绑定相同正式资产/特征，而不是随机描述“温柔女声”。

## 4. 模型能力登记与选用

所有模型都通过聚合中转站提供，**接入方式不是目前架构难点**，但用户指定的默认配置不能被误解为“所有能力已实测”。

- 文本模型首选（用户指定）：`deepseek-v4.1-flash`。
- 图片模型首选（用户指定）：`gpt-image-2`。
- 视频主力：MiniMax H3；Seedance / Wan3 可用于特定镜头、高质量尝试或后备方案。
- V1 业务规定：**单次视频 Generation Clip ≤15 秒**，即便某次模型路由允许更长，也不自动扩大全产品上限。
- 用户没有要求固定模型自动切换策略；跨模型切换应尊重编译合法性、艺术差异和费用授权。
- **用户报告存在**自部署 H3 原生续接；聚合站 RunningHub 路由不能未经验证就认定具备同一能力。

建议系统维护按路由/模型/模式的能力记录，其状态可分为“用户报告／文档声明／实际验证／不可用／待验证”。通过实际任务证据更新，而不是只靠名称猜测。

## 5. 每一次生成都应留下可追溯证据

Run 保存：Clip Plan 和编译输入的不可变版本、目标模型/路由、参考媒体列表、提交时间、实际请求记录（剔除认证凭据）、远端任务身份、运行状态、失败信息、媒体结果位置、续接父引用（如有）。

Take 保存：对应 Run、真实视频/音频文件、技术属性、预览及审片结果、实际起止连续性状态、用户选择记录。

**“成功”需分开说**：

1. **提交成功**：远端已接受任务。
2. **运行完成**：远端已返回结果。
3. **媒体可访问/可播放**：真实视频文件存在，格式和声音可检查。
4. **创作符合要求**：演员、镜头、对白、连续性和情感通过专业审片。
5. **可用于成片**：选定 Take 的特定区间满足剪辑和声音衔接要求。

不能把第 2 项当成第 5 项。

## 6. 真实媒体 QA：观察与计划分离

| 检查层级 | 客观检查 | 专业判断 |
|---|---|---|
| 文件技术 | 文件存在、视频可解码、实际时长、帧率/尺寸、音轨/采样率等 | 画面是否达到表达目标 |
| 人物/资产 | 是否使用预期角色/场景/道具参考 | 视觉身份是否可信、服装变化是否符合剧情 |
| 动作与表演 | 视频实际出现哪些动作、是否按事件顺序 | 情绪与潜台词能否被表演传达 |
| 摄影与镜头 | 有无实际切镜、构图变化和摄影机运动 | 是否保留导演镜头的表达意图 |
| 音画 | 对白、声音、同步、静音/环境声是否存在 | 说话情感、节奏、声音设计是否支撑戏剧 |
| 连续性 | 实际起止状态与上下游片段能否对上 | 断裂是否影响观众理解与观影体验 |
| 叙事 | 场景/Beat 所需信息是否被表现 | 整体冲突、转折、角色关系变化是否成立 |

LLM/多模态模型可以协助识别和解释问题，但应允许用户修正错误观察；如果模型没有实际看到或听到媒体，不能假装做过视频 QA。

## 7. 从 Take 到成片：轻量操作，不是忽略专业

第 6 区保留必要能力：

- 多 Take 对比、采用/拒用与标记原因；
- 选择源 Take 的入点/出点，非破坏性组织 Timeline Segment；
- 必要的转场和节奏微调，声音衔接与基本音量处理；
- 追踪来自剧本/导演/Clip/Run/Take 的源版本与审片意见；
- 时间线版本、实际渲染任务、媒体可播放验证及导出记录；
- 质量问题按根因回到第 1–5 区，而不是将第 6 区做成一个复杂通用后期软件。

**编辑顺序与生产顺序分离**。例如 22 秒长 Shot 分两次原生续接生成，在第 6 区可以是一段连续的叙事动作；如何拼接与是否可用由真实素材和审片决定，不因为技术上连了上下文就假装无缝。

## 8. 对 Codex 的未来验收要求

- 模型无关的 Clip Plan 能按目标模型/模式编译为合法输入；不能无理由丢失已确定的镜头、声音或关键参考。
- 任何缺媒体、时长违规、非法模式或不可用续接必须在提交前报告。
- 多次生成、重试和切换模型不会覆盖先前 Compiled Input / Run / Take。
- 用户可以实际播放和对比 Take，并看到其所属 Clip/Shot 与生成来源。
- 可以区分“完成但很差”“媒体损坏”“生成失败”“已经可用于成片”。
- Timeline Segment 是源视频的引用区间；修改时间线不删除源 Take。
- Render 必须是实际存在并经过技术检查的可播放文件。

本文件不执行真实 API 调用、费用或生成测试；具体请求合同必须在实测能力清单批准后才能落地。
